# FluxWP docker-wordpress

Production-ready WordPress stacks for **Coolify** and plain **Docker Compose**: tuned PHP and OPcache, real upload limits, healthchecks, pinned images, WP-Cron in a worker, optional Redis object cache, and one-switch install of the FluxWP Panel.

## Pick a stack

| Stack | Web server | Database | Object cache | Good for |
|---|---|---|---|---|
| `mariadb` | Apache + mod_php | MariaDB 11.8 LTS | none | Small sites, closest to the stock Coolify template |
| `mysql` | Apache + mod_php | MySQL 8.4 LTS | none | Hosts or tools that expect MySQL |
| `mariadb-redis` | Apache + mod_php | MariaDB 11.8 LTS | Redis 8.8 | WooCommerce, membership, busy admin |
| `nginx-fpm` | nginx 1.30 + PHP-FPM | MariaDB 11.8 LTS | Redis 8.8 | Most traffic per GB of RAM |

Every stack comes twice:

- `coolify/<stack>/docker-compose.yml`: one file to paste into Coolify. Config files are inlined, secrets are generated by Coolify.
- `compose/<stack>/`: plain Docker Compose with a `.env.example`. Works on any server with Docker.

## Coolify

1. **Projects › Add Resource › Docker Compose Empty**.
2. Paste `coolify/<stack>/docker-compose.yml` and **Save**.
3. Set your domain on the `wordpress` service (`nginx` service for `nginx-fpm`).
4. Optional, in **Environment Variables**:
   - `WP_ADMIN_EMAIL`: installs WordPress on the first deploy, so the install screen is never open to the internet. The admin user and password are Coolify's `SERVICE_USER_WPADMIN` / `SERVICE_PASSWORD_WPADMIN`.
   - `FLUXWP_SETUP=true`: installs and activates FluxWP Panel (flx-setup).
   - `WP_LOCALE=tr_TR`, `WP_TIMEZONE=Europe/Istanbul`, `WP_TITLE`, PHP limits (see below).
5. **Deploy**.

The config files show up under the service's **Storages** tab, where you can edit them.

## Docker Compose

```bash
git clone https://github.com/FluxWP/docker-wordpress.git
cd docker-wordpress/compose/mariadb        # or mysql, mariadb-redis, nginx-fpm
cp .env.example .env
# set DB_PASSWORD, DB_ROOT_PASSWORD (and REDIS_PASSWORD): openssl rand -base64 24
docker compose up -d
```

The site listens on `http://localhost:8080` (`HTTP_PORT`). For production, put a reverse proxy with HTTPS in front (Caddy, Traefik, nginx). WordPress detects HTTPS from `X-Forwarded-Proto`, and the real visitor IP is read from `X-Forwarded-For` when the proxy is on a private network.

Set `WP_URL` + `WP_ADMIN_EMAIL` to install automatically. With an empty `WP_ADMIN_PASSWORD`, a random password is printed once in `docker compose logs worker`.

## What changed compared to the stock Coolify template

| Stock template | Here |
|---|---|
| `wordpress:latest`, `mariadb:11` | Pinned: `wordpress:7.1-php8.4-*`, `mariadb:11.8`, `mysql:8.4`, `redis:8.8-alpine`, `nginx:1.30-alpine`. Patch updates arrive on pull, major/minor upgrades are your decision. |
| PHP defaults (2 MB uploads, 128 MB memory) | 128 MB uploads, 256 MB memory, 300 s execution, 5000 input vars, all from env |
| OPcache with image defaults | 192 MB, 30k files, 32 MB interned strings, JIT off (no gain for WordPress) |
| Healthcheck loads the home page every 2 s (PHP + DB on every probe) | Static file (Apache) or FPM ping through nginx every 15 s, with `start_period` |
| `depends_on` without condition | Waits for a healthy database and Redis |
| WP-Cron on page loads | `DISABLE_WP_CRON` + worker container runs due events every 60 s, so cron also runs on quiet sites |
| Install screen open after deploy | Optional automatic install with generated admin credentials |
| MariaDB defaults | utf8mb4, 256 MB buffer pool, `skip-name-resolve`, performance schema off (~100-400 MB RAM saved), `MARIADB_AUTO_UPGRADE` |
| - | `DISALLOW_FILE_EDIT`, `no-new-privileges`, no DB/Redis ports published, server tokens hidden, `wp-config.php`/`readme.html`/PHP in uploads blocked, real client IP behind the proxy |

## Settings

All optional. In Coolify they are environment variables, with Compose they go into `.env`.

| Variable | Default | |
|---|---|---|
| `PHP_MEMORY_LIMIT` | `256M` | Also `WP_MEMORY_LIMIT` |
| `PHP_UPLOAD_MAX_FILESIZE` | `128M` | Largest single upload |
| `PHP_POST_MAX_SIZE` | `128M` | Keep ≥ upload size |
| `PHP_MAX_EXECUTION_TIME` | `300` | Seconds |
| `PHP_OPCACHE_MEMORY` | `192` | MB |
| `PHP_TIMEZONE` | `UTC` | PHP `date.timezone` |
| `APACHE_MAX_WORKERS` | `20` | Apache stacks: max processes (~64 MB each) |
| `PHP_FPM_MAX_CHILDREN` | `10` | nginx-fpm: max PHP workers (~64 MB each, keep ≥ 4) |
| `DB_BUFFER_POOL_SIZE` | `256M` | ~50% of the RAM you give the database |
| `DB_MAX_CONNECTIONS` | `100` | |
| `REDIS_MAXMEMORY` | `128mb` | Cache only, no persistence, LRU eviction |
| `WP_URL`, `WP_TITLE`, `WP_ADMIN_USER`, `WP_ADMIN_PASSWORD`, `WP_ADMIN_EMAIL` | | Automatic install (Coolify fills URL, user and password) |
| `WP_LOCALE` | `en_US` | Language installed on first setup, e.g. `tr_TR` |
| `WP_TIMEZONE` | `UTC` | Site timezone on first setup |
| `FLUXWP_SETUP` | `false` | `true` installs FluxWP Panel (flx-setup) |
| `FLUXWP_SETUP_URL` | | Custom zip; default is `updater.fluxwp.com`, then the GitHub release |
| `WP_CRON_INTERVAL` | `60` | Seconds between cron runs |
| `WP_ENVIRONMENT_TYPE` | `production` | |
| `WORDPRESS_TABLE_PREFIX` | `wp_` | Only before the first install |

Anything else goes into `config/wordpress/wp-config-extra.php` (loaded from `wp-config.php`) or the other files in `config/`.

## The worker

`worker` runs `wordpress:cli` and does three things, all safe to repeat:

1. Waits for the WordPress files and the database.
2. On first start: installs WordPress (when `WP_ADMIN_EMAIL` is set), the language, the Redis Object Cache plugin and its drop-in (Redis stacks), and FluxWP Panel (`FLUXWP_SETUP=true`). Language and FluxWP Panel are done once, so later changes in wp-admin stay.
3. Runs due WP-Cron events every `WP_CRON_INTERVAL` seconds.

WP-CLI is available there too:

```bash
docker compose exec worker wp plugin list
docker compose exec worker wp search-replace 'http://old.test' 'https://new.example' --all-tables
```

`wp db cli/export/import` use the MariaDB client of the cli image; on the `mysql` stack use the `mysql` container instead (see below).

## Backup and restore

```bash
# database (MariaDB stacks)
docker compose exec -T mariadb sh -c 'mariadb-dump -uroot -p"$MARIADB_ROOT_PASSWORD" "$MARIADB_DATABASE"' > backup.sql
docker compose exec -T mariadb sh -c 'mariadb -uroot -p"$MARIADB_ROOT_PASSWORD" "$MARIADB_DATABASE"' < backup.sql
# database (mysql stack)
docker compose exec -T mysql sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' > backup.sql
# files (wp-content)
docker compose exec worker tar -C /var/www/html -czf - wp-content > wp-content.tgz
```

Coolify can also back up the database service on a schedule.

## Upgrades

- **WordPress core, plugins, themes**: from wp-admin as usual (minor core updates are automatic). The image tag only sets the PHP version and the files of a fresh install.
- **PHP / images**: change the tag (`wordpress:7.1-php8.4-apache` → `...-php8.5-apache`) and redeploy.
- **MariaDB**: `MARIADB_AUTO_UPGRADE=1` runs the upgrade step when you move to a newer tag. Take a backup first.

## Development

The compose files are generated from `config/`, `scripts/` and `tools/build.py`:

```bash
python3 tools/build.py          # regenerate coolify/* and compose/*
python3 tools/build.py --check  # what CI runs
```

Edit the source files, never the generated ones.
